# 03 — Database Schema

Engine: **libSQL (SQLite dialect)**, embedded file `data/aryesh.db`, WAL mode,
`foreign_keys=ON`. Accessed only through `packages/db` repositories.

## 1. The core storage decision: JSON bag, not EAV

Three candidate shapes for user-defined fields:

| Shape | Verdict |
|---|---|
| One physical table per entity type, `ALTER TABLE` per field | Rejected. Every user field change becomes a schema migration — violates R1 outright, and breaks under rename |
| EAV — `entity_values(entity_id, field_id, value)` | Rejected. Every read is an N-way self-join; sorting and filtering across fields is miserable; typed values need value-per-type columns. Correct in theory, unusable in practice |
| **One `entities` table with a validated JSON `data` column, plus explicit field metadata, plus generated columns for hot fields** | **Chosen** |

SQLite's JSON support (`json_extract`, `->>`) plus **generated columns with
indexes** gives us the best of both: schema-free writes, and index-speed reads on
any field the user promotes. Promoting a field to indexed is the *only* case
where a user action triggers DDL, it is additive, and it is reversible.

```sql
-- when a field is marked indexed:
ALTER TABLE entities ADD COLUMN f_<field_key> AS (data ->> '$.<field_key>') VIRTUAL;
CREATE INDEX idx_e_<field_key> ON entities(type_id, f_<field_key>) WHERE deleted_at IS NULL;
```

Denormalised hot paths are maintained as real columns because the graph, the
command palette, and every list view need them without a JSON parse: `title`,
`status`, `start_at`, `end_at`, `progress`, `amount`, `owner_id`. Each is written
from the role-mapped field on save. Role mappings are stable, so this stays
correct across renames.

## 2. Schema (abridged DDL — full version generated by Drizzle)

### Configuration layer

```sql
CREATE TABLE entity_types (
  id            TEXT PRIMARY KEY,           -- ULID
  key           TEXT NOT NULL UNIQUE,       -- immutable slug
  name          TEXT NOT NULL,              -- mutable display name
  name_plural   TEXT NOT NULL,
  icon          TEXT, color TEXT,
  description   TEXT,
  traits        TEXT NOT NULL DEFAULT '[]', -- JSON: ["progress","temporal"]
  role_map      TEXT NOT NULL DEFAULT '{}', -- JSON: {"progress":"fld_x","start":"fld_y"}
  title_template TEXT NOT NULL DEFAULT '{{name}}',
  default_view_id TEXT,
  is_system     INTEGER NOT NULL DEFAULT 0, -- seed-pack marker, still deletable
  sort_order    INTEGER NOT NULL DEFAULT 0,
  hidden        INTEGER NOT NULL DEFAULT 0,
  archived_at   INTEGER, deleted_at INTEGER,
  created_at    INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  version       INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE fields (
  id            TEXT PRIMARY KEY,
  type_id       TEXT NOT NULL REFERENCES entity_types(id),
  key           TEXT NOT NULL,              -- IMMUTABLE
  name          TEXT NOT NULL,              -- mutable
  kind          TEXT NOT NULL,              -- see 04 §2 (18 kinds)
  config        TEXT NOT NULL DEFAULT '{}', -- JSON, kind-specific
  required      INTEGER NOT NULL DEFAULT 0,
  unique_value  INTEGER NOT NULL DEFAULT 0,
  default_value TEXT,                       -- JSON
  sensitivity   TEXT NOT NULL DEFAULT 'none',  -- none|private
  indexed       INTEGER NOT NULL DEFAULT 0,
  ai_visible    INTEGER NOT NULL DEFAULT 1,
  help_text     TEXT,
  sort_order    INTEGER NOT NULL DEFAULT 0,
  deleted_at    INTEGER,                    -- soft: data survives, field hides
  created_at    INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  UNIQUE(type_id, key)
);

CREATE TABLE relation_types (
  id           TEXT PRIMARY KEY,
  key          TEXT NOT NULL UNIQUE,
  name         TEXT NOT NULL,               -- "contributes to"
  inverse_name TEXT NOT NULL,               -- "is advanced by"
  directed     INTEGER NOT NULL DEFAULT 1,
  cardinality  TEXT NOT NULL DEFAULT 'many_to_many', -- one_to_one|one_to_many|many_to_many
  from_types   TEXT NOT NULL DEFAULT '[]',  -- JSON allow-list, [] = any
  to_types     TEXT NOT NULL DEFAULT '[]',
  semantics    TEXT,                        -- contribution|dependency|ownership|reference|derivation
  weighted     INTEGER NOT NULL DEFAULT 0,  -- carries a numeric weight
  cascade      TEXT NOT NULL DEFAULT 'none',-- none|archive|delete on source removal
  style        TEXT NOT NULL DEFAULT '{}',  -- JSON: colour, dash, thickness
  is_system    INTEGER NOT NULL DEFAULT 0,
  deleted_at   INTEGER,
  created_at   INTEGER NOT NULL, updated_at INTEGER NOT NULL
);
```

`semantics` is the relation-level analogue of a trait: the progress engine cares
that an edge *is a contribution*, not that it is called `contributes_to`.

### Data layer

```sql
CREATE TABLE entities (
  id          TEXT PRIMARY KEY,             -- ULID
  type_id     TEXT NOT NULL REFERENCES entity_types(id),
  title       TEXT NOT NULL,
  subtitle    TEXT,
  data        TEXT NOT NULL DEFAULT '{}',   -- JSON, validated on write
  -- role-projected hot columns:
  status      TEXT, progress REAL, start_at INTEGER, end_at INTEGER,
  amount      REAL, currency TEXT, owner_id TEXT,
  -- system:
  pinned      INTEGER NOT NULL DEFAULT 0,
  archived_at INTEGER, deleted_at INTEGER,
  created_at  INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  created_by  TEXT NOT NULL,                -- "user" | "agent:<id>" | "workflow:<id>"
  updated_by  TEXT NOT NULL,
  version     INTEGER NOT NULL DEFAULT 1,
  schema_dirty INTEGER NOT NULL DEFAULT 0   -- set by a breaking field change
);
CREATE INDEX idx_entities_type   ON entities(type_id, updated_at DESC) WHERE deleted_at IS NULL;
CREATE INDEX idx_entities_status ON entities(type_id, status)          WHERE deleted_at IS NULL;
CREATE INDEX idx_entities_time   ON entities(start_at, end_at)         WHERE deleted_at IS NULL;
CREATE INDEX idx_entities_owner  ON entities(owner_id)                 WHERE deleted_at IS NULL;

CREATE VIRTUAL TABLE entities_fts USING fts5(
  title, subtitle, body, content='', tokenize='porter unicode61'
);

CREATE TABLE relations (
  id        TEXT PRIMARY KEY,
  type_id   TEXT NOT NULL REFERENCES relation_types(id),
  from_id   TEXT NOT NULL REFERENCES entities(id),
  to_id     TEXT NOT NULL REFERENCES entities(id),
  weight    REAL,                            -- contribution weight, 0..1
  data      TEXT NOT NULL DEFAULT '{}',      -- relations can have fields too
  valid     INTEGER NOT NULL DEFAULT 1,      -- 0 if endpoints violate constraints
  created_at INTEGER NOT NULL, created_by TEXT NOT NULL,
  deleted_at INTEGER,
  UNIQUE(type_id, from_id, to_id)
);
CREATE INDEX idx_rel_from ON relations(from_id, type_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_rel_to   ON relations(to_id,   type_id) WHERE deleted_at IS NULL;
```

Both direction indexes exist because graph traversal is bidirectional and this is
the hottest read path in the product.

### Memory layer

```sql
CREATE TABLE memories (
  id          TEXT PRIMARY KEY,
  class       TEXT NOT NULL,      -- goal|project|decision|preference|general|temporary
  title       TEXT NOT NULL,
  content     TEXT NOT NULL,
  source      TEXT NOT NULL,      -- JSON ActorRef + provenance (execution id, message id, file)
  confidence  REAL NOT NULL DEFAULT 1.0,
  importance  INTEGER NOT NULL DEFAULT 3,   -- 1..5
  status      TEXT NOT NULL DEFAULT 'active', -- proposed|active|archived|disabled
  pinned      INTEGER NOT NULL DEFAULT 0,
  expires_at  INTEGER, last_used_at INTEGER, use_count INTEGER NOT NULL DEFAULT 0,
  superseded_by TEXT REFERENCES memories(id),
  embedding   F32_BLOB(1024),                -- libSQL native vector
  created_at  INTEGER NOT NULL, updated_at INTEGER NOT NULL, deleted_at INTEGER
);
CREATE INDEX idx_mem_vec ON memories(libsql_vector_idx(embedding));
CREATE TABLE memory_links (
  memory_id TEXT NOT NULL REFERENCES memories(id),
  entity_id TEXT NOT NULL REFERENCES entities(id),
  relevance REAL NOT NULL DEFAULT 1.0,
  PRIMARY KEY (memory_id, entity_id)
);
```

Memories deliberately do **not** live in `entities`. Their lifecycle (decay,
expiry, supersession, confidence) and their access pattern (vector + graph
hybrid retrieval) are unlike anything user-shaped, and forcing them into the
generic table would pollute both.

`revisions` holds both the forward patch and its inverse, which is what makes
undo a lookup rather than a reconstruction.

## 3. Two kinds of migration — do not confuse them

| | **Code migration** | **User schema change** |
|---|---|---|
| Cause | We ship a new version | User adds/edits a field or type |
| Mechanism | Drizzle migration file, versioned in git | An `INSERT`/`UPDATE` into `fields` |
| Frequency | Rare | Constant |
| Requires restart | Possibly | Never |
| Reversible | Forward-fix | Undo via `revisions` |

The only overlap is the `indexed` promotion in §1, which runs additive DDL inside
a transaction with the metadata write.

**Breaking user changes** (narrowing a type, e.g. text → number; deleting a field
that has data; removing an option still in use) follow one path:

1. Impact analysis — count affected rows, list dependent formulas, views, widget
   bindings, workflows.
2. Present it: *"312 entities have a value in this field. 2 formulas and 1 widget
   reference it."*
3. Offer: convert with a cast (dry-run preview of failures), keep the old data in
   `data.__archived[key]`, or cancel.
4. Execute in a transaction; write a revision; mark unconvertible rows
   `schema_dirty` for a resolution queue rather than dropping data.

Data loss requires an explicit, typed confirmation, and an automatic export
snapshot is taken first.

## 4. Backup, export, restore

- **Snapshot**: `VACUUM INTO 'backups/aryesh-<ts>.db'` — hot, consistent, single
  file. Scheduled nightly and before every destructive operation. Retention with
  hourly/daily/weekly tiers.
- **Portable export**: a directory of JSON (`config/`, `entities/`, `relations/`,
  `memories/`) plus a manifest with schema version and checksums. Human-readable,
  diffable, git-committable, and importable into a fresh instance.
- **Restore**: pick a snapshot or an export; runs into a scratch DB and validates
  before swapping.
- Attachments and generated files live on disk under `data/files/<ulid>` and are
  referenced by handle; the export includes them.

## 5. Query notes

- Graph traversal uses recursive CTEs with an explicit depth bound and a visited
  set — never unbounded (see `05` §4).
- Progress roll-up is computed in application code over a fetched contribution
  subgraph, not in SQL. It needs trait dispatch and formula evaluation, which do
  not belong in the database.
- Aggregations for finance widgets are SQL, over the `amount`/`occurred_at` hot
  columns, grouped by a role-mapped category field.
- All list reads are keyset-paginated on `(updated_at, id)`. No `OFFSET`.
